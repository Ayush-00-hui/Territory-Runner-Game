⏱️ MINUTE 1 (0:00 – 1:00) : Hook & Server-Authoritative Architecture 0:00 - 1:00
"Good morning respected professors and examiners. My name is Ayush. In Territory Runner, I architected the server-authoritative backend, PostGIS spatial database, distributed concurrency control, and kinematic anti-cheat.

Traditional fitness trackers like Strava only record passive 1D polylines without real-world conflict. Territory Runner transforms outdoor workouts into an active spatial strategy platform where athletes physically capture arbitrary 2D closed-loop polygons. Because mobile devices operate in untrusted environments susceptible to GPS spoofing and clock manipulation, our core architectural rule is: the client proposes, but the server authoritatively validates, serializes, and commits."

⏱️ MINUTE 2 (1:00 – 2:00) : Spatial Concurrency & Kinematic Anti-Cheat 1:00 - 2:00
"The most complex engineering challenge was spatial concurrency control. When rival runners compete in the same park, multiple writes hit the same geographic polygons. Optimistic Concurrency Control fails because discarded PostGIS difference queries waste massive CPU. Redis Redlock introduces split-brain risk.

I solved this using PostgreSQL transaction-scoped advisory locks via pg_advisory_xact_lock. This serializes spatial mutations—ST_Union to claim territory and ST_Difference to carve rivals—with zero orphaned lock leaks.

Additionally, to prevent players from driving cars or using mock GPS apps, I authored a kinematic anti-cheat filter in Go. It enforces hard athletic velocity ceilings: 25 km/h for running and 50 km/h for cycling, with a max acceleration limit of 4.5 m/s², automatically rejecting vehicle spoofers."

⏱️ MINUTE 3 (2:00 – 3:00) : Idempotency, Verification & Handover 2:00 - 3:00
"When mobile clients submit runs in spotty network zones, retried requests can cause duplicate territory claims. I enforced strict idempotency keys in PostgreSQL: duplicate submissions return HTTP 200 with cached capture results without double-crediting XP or land.

To verify the backend, I authored 79 automated Go tests covering advisory lock stress, kinematic limits, and spatial transactions. Under load, our p95 transaction latency remains under 35 milliseconds, and the entire backend is containerized in Alpine Docker.

Now, I hand over to my teammate Gurudutt, who will present the mobile UI design and athletic design system."

AYUSH — Examiner Viva Defense Cheat Sheet

Top 4 killer examiner questions with rapid 15-second oral defenses
Examiner Defense
Q1: Why use PostgreSQL advisory locks (`pg_advisory_xact_lock`) instead of Redis Redlock or row locks?
15-Second Defense: "Row locks cannot lock rows that don't exist yet—like newly carved rival territory slices—and table locks freeze read queries. Redis Redlock requires managing dual state and risks split-brain errors under clock skew. `pg_advisory_xact_lock` executes inside the PostgreSQL kernel, serializes spatial writes cleanly, and automatically releases on commit or rollback."
📁 Implemented in: backend/internal/store/postgres.go#L180-L215
Q2: How does your kinematic filter avoid falsely flagging an athletic human sprinter?
15-Second Defense: "We use world-record human biomechanics. Sprinters top out at ~44 km/h for brief bursts but cannot sustain it, and humans exhibit natural acceleration-deceleration curves. Our running ceiling is 25 km/h sustained with a 4.5 m/s² acceleration ceiling over a sliding time window. Vehicles show prolonged high velocities across turns that easily trigger our 0.70 anomaly threshold."
📁 Implemented in: backend/internal/anticheat/kinematic.go#L45-L95
Q3: How does PostGIS `ST_MakeValid` handle self-intersecting 'bowtie' loops from GPS jitter?
15-Second Defense: "In OGC geometry, self-intersecting loops break simple feature rules and throw GEOS TopologyExceptions. We pass incoming WKT through ST_Multi(ST_CollectionExtract(ST_MakeValid(geom), 3)). Under the hood, GEOS splits bowtie self-crossings into valid multi-polygon sub-rings, and collection extract preserves only 2D polygons while stripping 1D antenna lines."
📁 Implemented in: backend/internal/store/postgres.go#L240-L260
Q4: How do you verify Firebase JWT tokens on the Go backend without calling Google on every request?
15-Second Defense: "We fetch Google's public JWKS certificates once on server startup and cache them in memory. Every incoming request is verified in-process using local asymmetric RS256 RSA public key cryptography. We only make a network call to refresh certificates if an unknown key ID (`kid`) is encountered."
📁 Implemented in: backend/internal/auth/verifier.go#L30-L75
