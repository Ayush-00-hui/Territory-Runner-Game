1. The Core Vision & Spatial Paradigm

The Problem with Existing Fitness Apps: Traditional apps (Strava, Nike Run Club) log passive 1D linear polylines. Existing location games (Ingress, Pokémon GO, Turf) enforce rigid, discrete spatial grids (Google S2 cells or Uber H3 hexagons) that disrupt athletic cadence with stop-and-go screen tapping.

The Territory Runner Paradigm:

  • Continuous 2D Organic Polygons: Athletes run closed loops around city blocks, parks, or paths to conquer arbitrary organic 2D geometries without artificial grid constraints.
  • Momentum-Preserving Lasso Snapping: Crossing an outgoing trail automatically extracts and captures the closed polygon while retaining the preceding trail, allowing continuous multi-loop running without session restarts.
  • Server-Authoritative Concurrency: All spatial mutations (ST_Union, ST_Difference) execute inside transaction-scoped PostgreSQL advisory locks (pg_advisory_xact_lock) to guarantee atomic, race-free spatial consistency.

2. Complete Mathematical & Geometric Algorithms

2.1 Segment Cross-Product Intersection & Lasso Snapping

When an athlete moves, segment $\overline{P_1 P_2}$ (current fix) is tested against every historical segment $\overline{P_3 P_4}$. The 2D cross-product line determinant is:

Denominator D = (x1 - x2)(y3 - y4) - (y1 - y2)(x3 - x4)
t = [ (x1 - x3)(y3 - y4) - (y1 - y3)(x3 - x4) ] / D
u = -[ (x1 - x2)(y1 - y3) - (y1 - y2)(x1 - x3) ] / D
  • Intersection Criteria: A valid intersection occurs iff $0 \le t \le 1$ and $0 \le u \le 1$.
  • Exact Snapping Point: $\mathbf{P}_{\text{int}} = (x_1 + t(x_2 - x_1), \; y_1 + t(y_2 - y_1))$.
  • Lasso Extraction: The closed polygon $[\mathbf{P}_{\text{int}}, P_{j+1}, \dots, P_{n-1}, \mathbf{P}_{\text{int}}]$ is carved. Breadcrumbs prior to $P_j$ are retained as the active trail.
  • Proximity Fallback: If no direct line crossing occurs, a $35\text{ m}$ proximity scan snaps to the nearest vertex that does not induce self-intersection.

2.2 Azimuthal Equidistant Centroid Tangent Projection + Gauss Shoelace

Planar Shoelace formulas fail on spherical Earth coordinates because longitude degrees shrink away from the equator ($\Delta x \approx R \cdot \Delta \lambda \cdot \cos\phi$).

1. Centroid: φ0 = (1/N) ∑ φi, λ0 = (1/N) ∑ λi
2. Local Tangent Projection (R = 6,371,000 m):
xi = R * (λi - λ0) * cos((φi + φ0) / 2)
yi = R * (φi - φ0)
3. Planar Shoelace (Gauss Area):
Area = 0.5 * | ∑ (xi * y_{i+1} - x_{i+1} * yi) |
Geometric Parity Verification
For athletic runs (< 5 km²), the planar projection error against PostGIS ellipsoidal ST_Area(geom::geography) is strictly < 0.2%. Across 7 shared golden test fixtures, Dart Clipper2 and Go PostGIS agree within < 0.5%.

2.3 PostGIS Topological Sanitation Pipeline

GPS noise causes bowtie self-intersections and duplicate vertices that trigger PostGIS TopologyException errors. The server sanitizes all incoming polygons:

ST_Multi(ST_CollectionExtract(
    ST_MakeValid(ST_SetSRID(ST_GeomFromText($1), 4326)), 
    3
))
  • ST_MakeValid: Resolves self-intersecting bowties into valid multipolygon sub-rings and dissolves collinear zero-area spikes.
  • ST_CollectionExtract(..., 3): Discards degenerate points (dim 1) and linestrings (dim 2), retaining strictly 2D polygons (dim 3).
  • ST_Multi: Standardizes output to geometry(MultiPolygon, 4326).

2.4 Donut Hole Ray-Casting Classification

When runners circle a city block enclosing an interior rival island or unclaimable structure, horizontal rays are cast to infinity ($+\infty, y$). By the Jordan Curve Theorem, points with an odd crossing count are interior; points with an odd nesting depth (depth 1, 3, ...) are classified as interior holes and assigned to FlutterMap's holePointsList to render transparent cutouts.

4. Distributed Systems & Concurrency Architecture

4.1 Transaction-Scoped Advisory Locking (pg_advisory_xact_lock)

Multiple athletes contesting the same territory sector serialize via PostgreSQL advisory locks: 

-- Transaction-scoped: Automatically released on COMMIT or ROLLBACK
SELECT pg_advisory_xact_lock(hashtext('territory_mutation_lock'));

-- Atomically update rival territories and union winner's geometry
UPDATE territories t SET geom = ST_Difference(t.geom, vl.geom) ...;
INSERT INTO territories (...) VALUES (...) ON CONFLICT (owner_id) 
DO UPDATE SET geom = ST_Union(territories.geom, EXCLUDED.geom) ...;
  • Why not OCC? OCC version conflicts cause cascading rollbacks and high retry latency when runners contest the same park.
  • Why not Redis Redlock? Redis dual-system coordination risks split-brain inconsistencies under network pauses or GC halts. PostgreSQL advisory locks run in-kernel and auto-release on transaction completion.
  • Pooler Caveat: Connect strictly via Session Mode (Port 5432). Transaction-mode poolers (port 6543) break advisory locks and prepared query execution plans.

4.2 WebSocket Presence Hub & Singleflight Coalescing

  • Decoupled Snapshotting: Takes a quick read-lock snapshot of connected clients and releases hub.mu.RUnlock() before evaluating database or friendship operations, preventing framing deadlocks.
  • Singleflight Coalescing: Under multi-runner GPS presence broadcasts, concurrent friendship lookups for the same sender coalesce through hub.sfGroup.Do(senderID, ...). Exactly one database query executes while all callers share the result.

4.3 Lazy Territory Strength Decay on Read

Instead of wasteful scheduled cron sweeps over millions of geometric rows: $\text{Strength}(t) = \max\left(0, 100.0 - 15.0 \times \Delta t_{\text{days}}\right)$. Evaluated lazily on read queries in $O(1)$ time. Defending runners reset strength to 100.0 on write.

5. Mobile Client Engineering & Hardware Hardening

5.1 Background GPS Tracking Hardening

  • Android: Configured an Android Foreground Service (FOREGROUND_SERVICE_LOCATION) with a persistent sticky notification displaying live workout metrics and an acquired CPU WakeLock (wakelock_plus) to prevent OS CPU sleep.
  • iOS: Configured UIBackgroundModes: location, allowsBackgroundLocationUpdates: true, and activityType: Fitness.

5.2 Crash Recovery Safety Box (RunRecoveryService)

Incoming GPS coordinates flush continuously to disk in Hive box active_run_recovery. Upon unexpected OS termination, the app detects unfinalized sessions on relaunch, restoring coordinates, duration, and live preview area without data loss.

5.3 Offline-First FIFO Sync Queue (SyncQueueService)

Runs serialize into Hive box sync_queue with client-generated idempotent UUIDs. Local Clipper2 renders instant optimistic previews. On network reconnection, runs flush sequentially with exponential backoff ($2\text{s}, 4\text{s}, \dots \max 60\text{s}$). Permanent 4xx client errors halt retries immediately to protect battery.

5.4 AMOLED Endurance Battery Saver Mode

  • Subpixel Physics: Modern AMOLED displays emit light per subpixel; pure black (#000000) draws $0\text{ mW}$.
  • Suspension: Suspends 60 FPS map tile repaints, territory shaders, and camera updates.
  • GPS Duty-Cycling: Relaxes GPS polling from 1 Hz ($1\text{s}, 2\text{m}$) to 0.33 Hz ($3\text{s}, 8\text{m}$), achieving 60–80% display power reduction during 2+ hour marathon training.

5.5 15-Second Zero-Interpolation Signal Gap Policy

Signal dropouts exceeding 15 seconds segment the track buffer rather than interpolating across unknown terrain. Dead-reckoning through urban canyons or tunnels risks hallucinating paths through impassable buildings or private property; resetting ensures every captured polygon represents physically verified athlete movement.

6. Security, Privacy & Zero-Trust Architecture

  • Firebase Auth RS256 JWT Verification: Server fetches and caches Google's public x509 certificates (respecting HTTP Cache-Control headers) and verifies token signatures via rsa.VerifyPKCS1v15 with crypto.SHA256.
  • Dual-Layer Privacy Exclusion Zones: Circular exclusion zones ($50\text{ m} - 2000\text{ m}$) centered around home/workplace coordinates. Coordinates inside active zones are excised from public GPX/GeoJSON exports, and WebSocket presence broadcasts to rivals are suppressed.
  • Social Anti-Abuse Integrity: Database unique symmetric index ON duels (LEAST(challenger, opponent), GREATEST(challenger, opponent)) prevents concurrent duplicate challenges. Self-challenges are blocked, XP stakes bounded $[0, 1000]$, and modality matching enforced.

7. Master Viva / Interview Defense Cheatsheet

Q1: Why use PostgreSQL advisory locks (pg_advisory_xact_lock) instead of OCC or Redis Redlock?
Defense: In territory conquest, multiple runners actively compete to carve the same contested city block. Under OCC, concurrent writes abort with version conflicts, causing cascading rollbacks and wasted CPU overhead re-executing expensive PostGIS differences. Redis Redlock requires managing dual-system state; network pauses or GC halts risk split-brain inconsistencies without monotonic fencing tokens. pg_advisory_xact_lock runs directly inside the PostgreSQL kernel, strictly serializes spatial operations, and auto-releases on COMMIT or ROLLBACK.
Q2: Why use the planar Shoelace formula on mobile while using PostGIS ST_Area on the server?
Defense: Evaluating spherical ellipsoidal geodesics (Vincenty or Karney) on mobile UI threads causes 60 FPS frame drops and drains battery. Local tangent projection followed by planar Shoelace computes in $O(N)$ with < 0.2% error for human running scales (< 5 km²). The client calculation is purely an optimistic preview; server PostGIS ST_Area(geom::geography) is the sole authoritative source of truth. Both engines agree within < 0.5% across 7 shared golden fixtures.
Q3: How does the presence dispatcher prevent WebSocket deadlocks, and why use singleflight?
Defense: The hub takes a quick read-lock snapshot of connected clients and releases hub.mu.RUnlock() before entering database operations, completely decoupling network framing from store I/O. Singleflight coalesces concurrent cache-miss lookups per sender so that exactly one database query executes while all waiting callers share the result. When friendships change, hub.InvalidateFriends evicts cached sets with zero staleness.
Q4: Why reject pure Figure-8 loops while accepting Lasso loops?
Defense: Pure Figure-8 loops ($A \bowtie B$) produce opposing loops that cancel each other out in EvenOdd fill rules or create topological ambiguity regarding sovereign intent; both engines reject them with INVALID_LOOP. In Lasso loops, a runner circles around an area and crosses their earlier trail; the engine snaps precisely at the intersection point, claims the loop, and retains the preceding trail so the runner can continue and close further loops in the same session.
Q5: Why evaluate territory decay lazily on read instead of running background cron sweeps?
Defense: Lazy evaluation ($\text{Strength} = \max(0, 100 - 15 \times \Delta t)$) eliminates wasteful scheduled cron sweeps over millions of inactive geometric rows. Defending runners reset strength to 100 on write, guaranteeing $O(1)$ query evaluation and zero background database I/O amplification.
Q6: Why zero-interpolation across GPS signal dropouts exceeding 15 seconds?
Defense: Dead-reckoning through urban canyons or tunnels risks hallucinating paths through impassable buildings or private property. Threshold $\Delta t > 15.0\text{ s}$ immediately segments the track buffer; resetting ensures every captured polygon represents physically verified athlete movement.
Q7: Why FCM HTTP v1 with OAuth2 RS256 instead of legacy Firebase server keys?
Defense: Google deprecated the legacy FCM API in June 2024. Legacy server keys were permanent strings that granted unrestricted access if leaked. FCM HTTP v1 requires short-lived (60 min) OAuth2 tokens signed with RS256 assertions using service account keys. The backend uses the pure Go standard library (crypto/rsa, crypto/sha256) and dispatches in detached goroutines (5s timeout) to prevent push latency from blocking the HTTP 201 response.
